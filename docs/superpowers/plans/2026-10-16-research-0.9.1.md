# Research 0.9.1 (verify, again, reuse, refresh) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the 0.9.x roadmap items from the [direction](../specs/2026-10-15-harness-research-direction.md):
`research verify`, `--again`, reuse (`start --from`, `find`, `approve`, `refresh`) and a disclosed
compatible-guidance fallback, as runtime 0.9.1.

**Architecture:** Every "do some of the work again" feature reuses the existing reassessment round
(`state.reassess`): a round names the questions to research and check again and the questions to
rewrite, and `advanceReassess` schedules research → check → (optional cross-check) → write →
review for just those. Rounds gain a `kind` (`reassess`, `again`, `refresh`, `import`). `verify`,
`find` and the approval check are read-only views over the record and the exported `facts.json`.
Import reads the portable `research/` folder (`output.json`, `facts.json`, pinned revisions), not
another project's private `.harness-research/` queue.

**Tech Stack:** Node ≥ 20, ES modules, `node:test`; no runtime dependencies.

## Decisions

These fill in what the direction leaves open. Each is the conservative reading of it.

1. **`verify` is read-only.** It takes the store lock to read a consistent record, writes nothing
   and does not bump the output revision. It does not need `--run`; if given it must match.
   Keys come from `--keys FILE` (a JSON array of keys, or any text: every `fact-<32 hex>` token in
   order of first appearance, so a Slides `outline.json` or a blueprint with `[R:key]` markers
   works as is) and/or repeated `--key`.
   Results per key: `confirmed`, `narrowed`, `superseded`, `rejected`, `stale`, `unchecked`
   (a candidate not yet checked) or `gone`. Each result carries the requested key, the canonical
   key when it differs, the assertion recorded under the requested key, the replacement (key,
   statement, status) at the end of any narrowing/merge/supersession chain, the revision kind and
   reason, and the cited source revisions. A narrowed or superseded key is never reported as
   confirmed, even though its replacement is. A `gone` key is looked up in this project's saved
   earlier runs and reported with that run ID when found. The answer says live sources were not
   re-read (that is `refresh`).
2. **`--again` is an option of `research reassess`:** `reassess --again ID,... [--reason TEXT]`.
   Only assessed questions can be researched again. Their checked facts stay current (they were
   checked and may be cited); their gaps are retired as history; coverage, verdict, assessment,
   headline and answer are reset; the research task carries the person's reason. The round
   researches, checks and rewrites just those questions. Changed sources found at the same time
   are included in the same round.
3. **`start --from PATH`** (repeatable) reads `PATH/research/` (or `PATH` itself when it is a
   research folder). The manifest must match `facts.json`, which must validate. Imported:
   sections, subjects, questions (with their assessments and answers), checked, stale and rejected
   facts with keys unchanged, aliases, revisions, conflicts, supersessions, gaps, missing angles,
   sources with their pinned text copied into this project, and checker identities. Not imported:
   unchecked candidates (their questions are researched again). Pinned text that is missing makes
   that source's facts stale (their questions are researched again); pinned text that does not
   match its recorded hash or quotes refuses the import. A supplied-only run does not import
   sources found on the public web, or facts resting on them (their questions are researched
   again with the run's own sources); sources a person selected for the origin are admissible.
   Claim questions come across only when their exact claim target exists unchanged in this
   project; `--claims` cannot be combined with `--from` (a fact-check is its own run). All origins
   must share a depth, which the new run keeps.
   The planner is asked to *extend* the plan (new questions only, possibly none) when the topic or
   `--about` differs from the single origin's, when new `--source`s are selected or when several
   origins are combined. Imported and new work that needs doing runs as one `import` round, which
   at any depth includes a cross-check (merges, conflicts, supersessions; no further gap questions)
   when it researches new questions. With nothing to do, the run is complete at once. Section,
   subject and question IDs that collide between origins with different content are renamed with
   a numeric suffix; identical questions are shared and, when facts for them come from more than
   one origin, researched and checked again so one checker assesses their coverage. Origins are
   recorded in `origins`, with their approvals as history, never as approval of the new run.
   Editing the plan with `continue --file` is refused for an imported run.
4. **`find --in DIR [--query TEXT]`** walks DIR (at most 6 levels, no symlinks, skipping hidden
   directories and `node_modules`) for `research/output.json` owned by this helper, and lists each
   folder's topic, title, run, status, depth, dates, counts, approval, oldest/newest source dates
   and whether its exports are consistent. `--query` keeps folders whose title, topic or questions
   contain every query word.
5. **`approve --by NAME [--revision N]`** needs a `complete` or `complete-with-gaps` run. It
   records who approved, when, the output revision they saw, and a digest of the approved content
   (plan, questions, answers, facts, sources and their revisions, gaps, conflicts). The approval is
   current only while that digest still matches and no input is stale; `status`, the report,
   `facts.json`, `verify` and `find` show whether it still applies. `--revision` refuses the
   approval if the research changed after the person looked at it.
6. **`refresh`** needs a finished run with no stale inputs (a changed local file is `reassess`).
   Local selected files are checked by hash already, so refresh tasks cover sources whose origin is
   a web link, up to 10 per task. A worker re-reads each original and submits its current full text
   (or `read_original:false` with an access error). The helper checks mechanically whether every
   passage quoted from that source still occurs in the current text: facts with a vanished passage
   become stale and their questions are researched, checked and rewritten in a `refresh` round;
   changed text is registered as a new revision of the source and the old one is marked superseded.
   An unreadable original leaves its facts current and is reported as not re-read.
7. **Guidance freshness:** when `sync-guidance start` skips newer releases that need a newer
   runtime, it reports `freshness: "older-compatible-release"`, the newest release and the runtime
   it needs, and a notice to update with the trusted installer. A failed fetch still fails.
8. **Versioning:** runtime and guidance become 0.9.1; the guidance minimum runtime stays 0.8.1 and
   the new commands are routed through a new `references/reuse.md` that says they need runtime
   0.9.1. Do not merge to `main` before the release is tagged (helpers ≤ 0.8.1 read `main`).

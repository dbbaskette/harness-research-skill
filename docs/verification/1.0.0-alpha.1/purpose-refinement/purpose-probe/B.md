# What to understand before replacing Redis with Valkey

Replacing Redis involves moving data and deciding which server will accept application writes. For Redis OSS 7.2 and earlier, Valkey supports the same communication protocol and compatible saved-data formats, so existing Redis clients can connect. That compatibility has a boundary: Redis CE 7.4 and later produce data files that Valkey cannot use through the documented file-based route. First identify the Redis version; a familiar client connection does not establish file compatibility. [Source: migration.txt](../../valkey-redis/research/sources/migration.txt)

One migration method copies a snapshot: a saved picture of the dataset at a particular point. Valkey loads that picture into memory when it starts. Writes made after the picture was taken would be missing, which explains the guide's requirement to disconnect active connections before creating the migration snapshot. This approach also involves downtime while Redis stops and Valkey loads the data. [Source: migration.txt](../../valkey-redis/research/sources/migration.txt)

Replication keeps a second server updated. The primary accepts writes and sends changes to a replica. During a full synchronization, it creates a snapshot while buffering new writes, transfers the snapshot, then sends the buffered changes. After a broken connection, a replica can request just the missing changes if the primary still has them in its backlog, a retained portion of the change stream. Otherwise, it needs another full synchronization. [Source: replication.txt](../../valkey-redis/research/sources/replication.txt)

Consider an illustrative sequence: Redis accepts a change to a key, but fails before its Valkey replica receives that change. The replica can have the older value even though the application received a successful write response. This follows from asynchronous replication: the primary does not wait for every replica to process each write. A connected replica is therefore not necessarily current at every instant. `WAIT` can request acknowledgements from replicas, but it still does not guarantee that writes survive every failover. [Source: replication.txt](../../valkey-redis/research/sources/replication.txt)

For migration, Valkey can first follow Redis as a replica and later become the primary; replicas reject writes by default. Copying data and taking responsibility for writes are distinct steps. Replication is also not a substitute for persistence, which saves data for restart: a primary that restarts empty without persistence can make its replicas copy that empty state. Understanding these mechanisms explains why a migration must account for active writes, promotion and restart behavior. [Sources: migration.txt](../../valkey-redis/research/sources/migration.txt), [replication.txt](../../valkey-redis/research/sources/replication.txt)

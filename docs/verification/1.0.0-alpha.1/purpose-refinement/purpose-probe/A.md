# What to understand before replacing Redis with Valkey

A migration pilot is worth considering when the fleet runs Redis OSS 7.2 or earlier and the team has a concrete reason to pursue Valkey. The supplied migration guide supports technical feasibility for that boundary: compatible protocol, configuration and RDB/AOF formats, existing Redis clients, Lua scripts using the `redis` namespace, and modules built against the Redis OSS module API. Redis CE 7.4 and later produce incompatible data files; the guide does not establish an alternative migration method for those versions. My recommendation is to fund a bounded compatibility and cutover pilot for the former group, and resolve the transfer method before funding the same pilot for the latter. [Source: migration.txt](../../valkey-redis/research/sources/migration.txt)

The migration method determines what the pilot must prove. Snapshot transfer requires an interruption while Redis stops and Valkey loads; active connections must be disconnected before the snapshot to prevent missed writes. If AOF is enabled on the destination, it must be disabled on the first start or the copied RDB will not be imported. Replication can reduce downtime, but ongoing writes during shutdown can still cause data loss. Cluster migration adds Valkey replicas, promotes replacements for each Redis primary, and removes Redis nodes. These are different operational exercises, so the pilot should match the production topology and rehearse write coordination and promotion. [Source: migration.txt](../../valkey-redis/research/sources/migration.txt)

The key acceptance boundary is data safety. Valkey replication is asynchronous, and even `WAIT` does not guarantee that acknowledged writes survive every failover; persistence configuration matters. A primary that restarts empty with persistence disabled can cause replicas to discard their data too. Consequently, I recommend validating recovery behavior as well as the successful transfer path. [Source: replication.txt](../../valkey-redis/research/sources/replication.txt)

These documents justify investigation, not a fleet-wide business case. They supply no workload-specific performance or cost results and no demonstrated rollback for this fleet. Staying with the current deployment remains a reasonable interim choice if its requirements are met and migration has no established benefit, or if the proposed cutover cannot satisfy the team's loss tolerance. Pilot funding should therefore buy evidence about actual application dependencies, transfer correctness, outage duration and recovery, with rollback still an explicit unresolved item. These are recommendations based on the documented compatibility and failure boundaries, not reported test results. [Sources: migration.txt](../../valkey-redis/research/sources/migration.txt), [replication.txt](../../valkey-redis/research/sources/replication.txt)
